# Limen media generation endpoints — specification

Status: DRAFT. Awaiting ratification. No code changes follow from this
document until ratification. Implementation starts only after
ratification, in the phases of section 11.

Date: 2026-11-23. Scope: the Limen OpenAI-compatible shim (`ai/limen/`).
Builds on: the hybrid streaming work (PR #213) and the model routing
work (PR #214). Implement after both merge, in that order.

## 1. Purpose

The shim serves chat today. It does not serve image or video generation.
Clients that use the shim for chat cannot generate media through it.
This specification adds image and video generation endpoints to the shim.
It uses only the gadget credential. It uses no web credential. It uses no
browser.

## 2. Hypothesis

The hypothesis has three parts. First, users of the shim need media
generation through the same OpenAI-compatible surface as chat. Second,
the agent behind the shim can generate media for turns sent through the
gadget credential. Third, the shim can fetch the generated bytes over
the gateway tunnel with that credential.

Live probes verified the second and third parts on 2026-11-23. A turn
sent through the gadget credential produced an image. The reference to
the file arrived in the transcript. A raw GET on the gateway tunnel
returned the exact bytes. The file verified as a genuine image with the
recorded dimensions. The probes also fixed the mechanism: the chunked
POST file read is denied for this credential, and the raw GET is in
scope. Video generation is not verified. No video turn has run.

Alternatives considered and rejected: a browser shim reads rendered
pages with a logged-in browser and user cookies. The shim deliberately
avoids that credential and that mechanism. A gateway-protocol shim
polls history like the web client. It offers no streaming for gadget
turns and no advantage over the current shim. The workspace-save path
asks the agent to write the file into the gadget workspace. It is
unnecessary now that the raw GET delivers the bytes directly.

Kill criteria, all resolved: if the agent refused media turns, or if no
route returned the bytes, this specification would stop here. Neither
happened. The remaining kill criterion is video: if the video probe
(section 14, D2) shows the agent cannot generate video for gadget
turns, the video phase stops and the image phases still stand.

## 3. Proven facts

The design rests on these facts. Each fact was verified live.

1. The gadget credential reaches four gateway routes: history, stream,
   subscribe, and stream events. It does not reach session management
   routes. The server refuses those with a 403.
2. The chunked POST file read is denied (403) for the gadget credential.
   The file stat route is denied too. The media raw route is denied too.
3. The raw GET file route is in scope. A GET on a real generated path
   returned exactly the recorded byte count. The file verified as a
   genuine image with the recorded dimensions.
4. A media turn sent through the gadget credential generates an image.
   The reply text carries no media reference. The reference lives in
   the presentation event in the transcript. The event carries the file
   path, the MIME type, the dimensions, and the byte count.
5. Live deltas arrive only for main-chat turns. A media turn in a thread
   yields no live deltas. The transcript still carries the finished
   presentation event. The shim must read the transcript, not the reply
   text and not the live stream, to find generated media.
6. The wait path caps at 600 seconds. The service enforces the cap.
   Generation longer than the cap cannot complete inside one wait.
7. The agent obeys gadget turns, with one observed exception: an
   API-injected turn was refused once on origin grounds, with a refusal
   sentence. The refusal is context-dependent, not a blanket rule.

## 4. Scope

In scope: synchronous image generation, image edits with reference
images, asynchronous video generation with polling, a public media
route that serves stored files, and the model entries that advertise
image and video models.

Out of scope: media streaming, prompt-injected tool calling as a
feature, multi-account pools and failover, automatic approval of
approval cards, any model alias that reaches another provider, and any
browser or cookie mechanism. Image generation for the main chat is out
of scope: media turns always start a fresh session.

## 5. Endpoint contracts

The shim dispatches all POST routes in one handler. Media routes join
that handler. Error responses use the existing error shape. Usage
tokens stay `0`, as in chat today.

### 5.1 POST /v1/images/generations — synchronous

Request body (OpenAI shape): `prompt` (required), `model` (default
`muse-image`), `size` (optional aspect hint), `n` (must be `1`),
`response_format` (`url` or `b64_json`, default `url`), `timeout`
(optional, default 240 seconds).

Flow: build a plain media prompt from the request. Send it as a fresh
session through the wait path. Read the transcript for the presentation
event. Fetch the bytes with the raw GET. Store the bytes. Return the
response.

Response: `{created, data: [{revised_prompt, url | b64_json, size,
kind, bytes}]}`. `revised_prompt` is the request prompt. No upstream
revised prompt is known. `size` reports the delivered file's actual
dimensions. `kind` is `image`. `bytes` is the delivered byte count.
With `b64_json`, the response inlines the bytes and drops the URL.

Failure rules: a request with `n` other than `1` gets a 400. An
unknown `response_format` gets a 400. A timeout gets a 502. A refusal
sentence gets a 502. A text-only reply after the grace period in
section 6 gets one follow-up turn that asks to attach the file, then a 502. A file delivered when a video was expected cannot happen here.
Only bytes on disk count as delivery. A success claim in text is never
delivery proof.

### 5.2 POST /v1/images/edits — synchronous

Request: multipart form-data (`image` files plus `prompt`) or JSON.
The local socket takes one image per send. Multiple references need
sequential turns or one composite image. The implementation decides and
documents the limit.

`mask` is rejected with a 400. The agent cannot inpaint a region.
Never silently ignore a mask. A missing image gets a 400. Otherwise
the flow and the failure rules match section 5.1.

### 5.3 POST /v1/videos and POST /v1/videos/generations — asynchronous

Video generation can exceed the 600-second wait cap. The endpoint is
always asynchronous. It returns immediately:
`{id, task_id, object: "video.task", status: "queued", progress: 10}`.

### 5.4 GET /v1/videos/{task_id} — task polling

The poll returns the task record: `id`, `kind`, `status`, `progress`,
`result`, `error`, `created_at`. A completed task carries the media
URL and the file metadata. An unknown task ID gets a 404.

### 5.5 GET /v1/media/{name} — serving stored bytes

The route serves a stored file by name. The route is intentionally
public. Clients cannot send auth headers, so unguessable random names
provide the protection. The route sets
`Cache-Control: public, max-age=86400`. An unknown name gets a 404.

### 5.6 GET /v1/models

The model list advertises `muse-image` and `muse-video` next to the
chat models. The default model and the aliases stay as the routing
work defines them.

## 6. Media flow

One pipeline serves every media endpoint. The steps:

1. Build a plain media prompt from the request. The prompt states a
   fresh creation. It names no history.
2. Send the prompt as a fresh session through the wait path. Media
   turns always start a fresh session. The caller's session stays
   clean, and the reply is unambiguous.
3. Read the transcript for the presentation event when the wait
   completes. The image flow reads history after the wait. It opens no
   subscription. The finished presentation event is in the transcript
   even when no live delta arrived.
4. Fetch the bytes with the raw GET on the gateway tunnel.
5. Store the bytes in the media store.
6. Return the response in the endpoint shape.

If step 3 finds no reference, the flow sends one follow-up turn that
asks to attach the file, then repeats step 3 once. If the reference is
still absent, the flow fails with a 502. The image flow waits up to
the request timeout (default 240 seconds). The video worker has no
HTTP wait: it polls the transcript in the background until the
presentation event appears or the worker timeout ends.

## 7. Media store

The store holds delivered bytes under the container's workspace mount.
It never uses the agent sandbox. It never uses the container's
writable layer.

Rules: filenames are uuid-random, never sequential or guessable. A
strict safe-name pattern rejects any name with a separator or a
traversal. The public route serves only names that match the pattern.
The store prunes files older than the retention period (decision D4).
Prune is a Phase 1 test target, not an afterthought.

## 8. Video task store and worker

The task store is in-memory first. A task record holds `id`, `kind`,
`status`, `progress`, `result`, `error`, `created_at`. A restart loses
in-memory tasks. This limitation is stated, not hidden. Persistence
under the workspace mount is a later change if a restart-safe record
is needed.

Each video task runs a background worker thread. The worker uses the
same worker-thread pattern as the streaming work: one send with the
wait path, transcript polling for the presentation event, byte fetch
on success. Progress moves from `queued` (10) through `running` to
`completed` or `failed`. The poll endpoint reads the store. It never
blocks on generation.

## 9. Error taxonomy

- 400 `invalid_request`: `n` other than `1`, unknown
  `response_format`, `mask` present in an edit, missing image in an
  edit.
- 401 `invalid_api_key`: auth failure, as in chat today.
- 404 `model_not_found`: unknown model alias. 404 for an unknown video
  task ID and for an unknown media name.
- 502: timeout, refusal sentence, text-only reply after the follow-up,
  wrong-kind delivery (an image delivered when a video was expected, or
  the reverse). A 502 never carries a success claim.

## 10. What this design excludes

The design excludes the browser and cookie mechanism, DOM-scraped
streaming, typewriter smoothing, prompt-injected tool calling as a
feature, multi-account pools and failover, automatic approval of
approval cards, any model alias that reaches another provider, the
chunked POST file read, the workspace-save path, and media turns in
the main chat. Section 4 lists the same exclusions as scope. This
section restates them so a reviewer checks them in one place.

## 11. Implementation phases

One pull request per phase. One commit per file per pull request.
Branch from master after the streaming work and the routing work merge,
in that order. If they are still unmerged when work starts, stack on
the routing branch and say so in the pull request body. Each pull
request body states the rationale. The next phase starts only on green
CI.

1. Phase 1 — media store plus `GET /v1/media/{name}`. New store module
   with uuid names, safe-name guard, and prune, plus the route and its
   tests. No generation yet. The route serves files the tests write.
2. Phase 2 — `POST /v1/images/generations` (synchronous). Media prompt
   builder, fresh-session send through the wait path, transcript scan,
   byte fetch through the raw GET, store plus URL or `b64_json`
   response. Tests use a mocked send and fake bytes.
3. Phase 3 — `POST /v1/images/edits`. Multipart parsing, reference
   handling through the socket image field, `mask` rejection. Tests
   cover multipart and JSON, mask rejection, missing image.
4. Phase 4 — `POST /v1/videos` plus `GET /v1/videos/{task_id}`. Task
   store plus background worker. Tests cover the task lifecycle,
   unknown ID, and progress values. The video probe (decision D2) runs
   before this phase.
5. Phase 5 — models plus docs. `muse-image` and `muse-video` in the
   model list. Media section in the overview document. readme pointer.

## 12. Tests and verification

Unit tests live next to the code they cover. They cover response
shapes, `url` versus `b64_json`, mask rejection, unknown task 404,
name-validation rejection, timeout and refusal as 502, and transcript
parsing of presentation payloads. The coverage gate is 90 percent.
`mypy --strict` runs clean. `ruff check` and `ruff format --check`
run clean. CI is the source of truth for formatting: never commit
wholesale local formatter output. `prettier` runs on touched docs only.

Live verification needs the owner, with root on the deployment host:
merge, master CI green, container refresh, verify the running
container is fresh plus a health check, one real image turn on a fresh
session through the public endpoint, fetch the returned media URL and
confirm the bytes, one video task polled to completion. Commit and
pull request text never name a verification subject.

## 14. Decisions for ratification

- D1. Ratify this scope: synchronous image generation, image edits,
  asynchronous video generation with polling, public media route, and
  the model entries.
- D2. Run a video probe before Phase 4: one video turn, to confirm the
  presentation payload and the asynchronous flow for video.
- D3. Edits with multiple references: sequential turns or one composite
  image. The implementer decides and documents the limit.
- D4. Media retention default: proposed 7 days.
- D5. Deploy per phase, or batched after Phase 2.
- D6. SDD onboarding for this repository: this specification is a design
  document under the normal workflow. The implementation is the next
  feature change on a project that has not adopted the specification
  cycle. The onboarding question applies before implementation starts:
  adopt the cycle (the specification moves to the feature directory,
  a constitution draft, a first decision record, and a continuity
  test), or proceed normally.

## 15. Residual risks

- Video is unproven. Decision D2 covers it.
- The agent refusal is context-dependent. A media turn can fail with a
  refusal sentence. The failure surfaces as a 502. It is visible, not
  silent.
- The store grows if prune fails. Prune is a Phase 1 test target.
- The public route trades auth for unguessability. Names must stay
  uuid-random, never sequential.
